01

Start here

One Git repository describes the machine, your desktop and your portable tools. Edit the repository, build it, test it, then switch. GitHub shares the source; Nix builds it; Home Manager installs your user configuration.

Everyday changes

Edit → test → switch

Use your existing host name. Updating a setting does not require updating all packages.

Another computer

New host, shared desktop

Add its hardware and boot settings under hosts/. The same desktop profile is imported automatically.

Just the tools

Run without installation

The CLI bundle and configured editor work independently of the desktop and Home Manager.

Current support: this repository targets x86_64-linux. The full desktop has been tested in the existing NixOS QEMU VM. ARM, Apple Silicon, physical GPU behaviour and other operating systems are not validated targets. Individual upstream packages supporting them does not make this whole desktop portable.

Source repository · Guide prepared 12 September 2026 · The standard checkout on each installed machine is /etc/nixos. Commands assume a terminal there unless stated otherwise.

02

How the pieces fit

Git + flake.lockSource and exact dependency revisions
→
NixOSHardware, boot, accounts and system services
+
Home ManagerUser files, packages and desktop services
+
Wrapped packagesPortable applications with their settings

flake.nix declares upstream inputs. flake.lock fixes the revisions and source hashes. import-tree loads the Nix files in modules/; flake-parts assembles their outputs. The explicit desktop profile in modules/flake.nix combines named NixOS features. Each directory in hosts/ becomes a nixosConfigurations entry.

Most feature files still define flake.modules.nixos.<feature>. They contribute user settings through home-manager.users.tongy. This keeps related system and user configuration close together, instead of collecting everything in a giant home file.

OwnerWhat belongs thereExamples here
NixOSThings that establish or serve the machineBootloader, filesystems, users, SDDM, Hyprland session integration, PipeWire, NetworkManager, Tailscale, Steam integration and Syncthing's system service
Home ManagerThings belonging to your loginGTK preferences, MIME defaults, desktop entries, Hyprland config files, Vicinae, clipboard history and authentication agent
WrappersA runnable application with config and dependencies attachedZsh, tmux, Git, Ghostty, Neovim and btop
Ordinary application dataMutable state that is not declared in GitAccounts, browser profiles, notes, histories, saves and credentials

Home Manager uses the system's package set and installs user packages into /etc/profiles/per-user/tongy. It activates as home-manager-tongy.service during the NixOS rebuild. There is no standalone homeConfigurations output or separate Home Manager switch workflow in this repository.

Asset files are configuration sources. Copying one to another computer is not a second installation process. Nix modules reference them and Home Manager or a wrapper deploys them.

04

Your everyday workflow

Use the host directory name in the rebuild target. Below, my-pc is an example; replace it with a host that actually exists. Use nixos-vm only inside the existing VM.

cd /etc/nixos
git pull --ff-only
# Edit the relevant module or asset.
git diff
# Stage new files so the Git-backed flake can see them.
git add modules assets hosts tests
nix fmt -- flake.nix modules/*.nix hosts/my-pc/*.nix
nix flake check
nix build .#checks.x86_64-linux.caelestia-config .#checks.x86_64-linux.portable --no-link
nix build .#checks.x86_64-linux.portable .#checks.x86_64-linux.caelestia-config --no-link
sudo nixos-rebuild test --flake .#my-pc
bash tests/home-manager.sh
# Once the desktop behaves as expected:
sudo nixos-rebuild switch --flake .#my-pc
git commit -m "Describe the configuration change"
git push

git add makes new files visible to a flake; it does not publish them. git commit records a revision locally. git push publishes commits to GitHub. None of those commands applies the configuration to other computers. Each machine must pull and rebuild separately.

CommandEffect
nixos-rebuild buildBuilds without activation
nixos-rebuild testActivates for the running system, without making it the boot default
nixos-rebuild switchActivates now and updates the boot default
nixos-rebuild bootPrepares the configuration for the next boot without activating it now

A test activation still changes running services and user settings. It is not a dry run. Use build when you only want to check compilation. Restart an app if it caches its settings; a fresh desktop login also refreshes session environment and application discovery.

New Nix files need valid flake-parts module contents because import-tree loads the directory. Adding a named feature does not automatically add it to the explicit desktop imports.

05

Installing and updating apps

For a package already in nixpkgs, add it to home-manager.users.tongy.home.packages in the relevant feature. For a service or system integration, enable its NixOS module as well. Installing a binary alone does not configure its service.

# Inside a NixOS feature module with pkgs in its arguments:
home-manager.users.tongy.home.packages = with pkgs; [
  obsidian
  bitwarden-desktop
  # Add another nixpkgs package here.
];
ApplicationPackage sourceUpdate mechanism
Zenzen-browser-flake, beta packageUpdate the zen input. Its Home Manager dependency follows ours.
HeliumHelium community flakeUpdate helium; the maintained package downloads and adapts upstream releases.
ChatGPTNumtide llm-agents.nixUpdate llm-agents; its package adapts the official Linux payload and downloaded runtimes for NixOS.

Helium and ChatGPT remain available as .#helium and .#chatgpt. Versions and hashes now live in the pinned upstream flakes instead of a locally maintained download recipe. This does not remove compatibility work; the package maintainers own it.

# Updating only these applications:
nix flake update zen helium llm-agents

# Or deliberately update every input, including nixpkgs and Home Manager:
nix flake update

# Inspect, build, test and switch before committing the new lock file.
git diff -- flake.lock
nix flake check
nix build .#checks.x86_64-linux.caelestia-config .#checks.x86_64-linux.portable --no-link
sudo nixos-rebuild test --flake .#my-pc
sudo nixos-rebuild switch --flake .#my-pc
git add flake.lock
git commit -m "Update pinned dependencies"
git push

The current package set follows nixos-unstable, but a rebuild uses the locked revision until you update it. Keep the lock file in Git. Application auto-updaters should not be your update workflow for Nix-managed binaries.

The tested replacements were Helium 0.16.6.1 and ChatGPT 26.908.40834. The official ChatGPT Linux app remains a preview for selected distributions; its Nix package is community maintained. The VM launch check reached its sign-in screen, not an authenticated end-to-end agent session.

06

Use the tools without the desktop

On another supported x86_64 Linux machine with Nix and flakes enabled, you can run the configured tools without applying Home Manager or replacing that computer's dotfiles.

nix run github:itstongy/nixos-config#shell
nix run github:itstongy/nixos-config#neovim
nix run github:itstongy/nixos-config#ghostty
nix shell github:itstongy/nixos-config#cli
nix profile add github:itstongy/nixos-config#cli

nix develop github:itstongy/nixos-config#python
nix develop github:itstongy/nixos-config#node
nix develop github:itstongy/nixos-config#rust
nix develop github:itstongy/nixos-config#nix

The wrappers carry their settings in the Nix store. Histories, editor state and caches remain writable. The CLI bundle includes the configured shell, Git, tmux, Neovim and btop alongside supporting tools. Use a Nerd Font in your host terminal for the intended icons.

nix run executes an app; nix shell temporarily adds packages to a shell; nix profile add persists them in a user profile; nix develop enters a development environment. The language shells are starting points. Each real project should pin its own dependencies.

The full desktop is a NixOS deployment. This repository does not yet offer a standalone Home Manager desktop for another distribution. Graphical packages on non-NixOS hosts can also need host-specific graphics integration; that path has not been validated here.

07

Add another machine

This desktop is prepared as tongynix. Its host captures the i7-6700K, GTX 1080 with NVIDIA legacy 580, both 1440p displays and the three existing storage drives. The fresh-install layout uses an ext4 root labelled tongynix-root and a FAT32 EFI partition labelled TONGYBOOT. Follow the tongynix installation instructions. On the installed desktop, use cd /etc/nixos and sudo nixos-rebuild switch --flake .#tongynix. The full host system builds successfully, including the NVIDIA kernel module. Physical graphics, suspend and installation still need verification on the real machine.

/etc/nixos is the standard location for this setup, including its flake, lock file, modules and all host definitions. Nix can use a checkout anywhere, but keeping this path consistent makes day-to-day commands easier. Each machine has its own Git checkout and selects its own host output. The development checkout and VM test directories used during this migration do not need to move.

The following setup preserves the existing directory. If /etc/nixos.before-flake already exists, stop and choose a fresh backup name before proceeding. Do not clone over an existing checkout. On a machine with the repository already installed, use cd /etc/nixos and pull instead.

Install NixOS normally first if you are new to it, keep the generated hardware and boot settings, then apply this desktop. The existing VM host is a machine record, not an installation template.

Changing to another username is currently a repository refactor, not a single host option. References to tongy exist in Home Manager, the account definition, services and profile paths.

# Run once on an existing NixOS installation.
# Stop if /etc/nixos is already this repository.
# Keep the original generated configuration as a backup.
sudo mv -T --no-clobber /etc/nixos /etc/nixos.before-flake
sudo install -d -o "$(id -un)" -g "$(id -gn)" /etc/nixos
git clone https://github.com/itstongy/nixos-config.git /etc/nixos
cd /etc/nixos
mkdir -p hosts/my-pc
sudo nixos-generate-config --show-hardware-config > hosts/my-pc/hardware-configuration.nix
# Create hosts/my-pc/default.nix using your existing boot settings.

The hardware command describes the currently running machine. Run it on the target NixOS installation, not on this VM or an unrelated workstation. Keep the backed-up /etc/nixos.before-flake/configuration.nix for reference while preparing the new host.

{ ... }: {
  imports = [ ./hardware-configuration.nix ];
  nixpkgs.hostPlatform = "x86_64-linux";
  networking.hostName = "my-pc";

  # Copy the working bootloader settings from this machine's installation.
  # Preserve its existing system.stateVersion exactly.
  # Do not use this incomplete example until those settings are present.

  tongy.dictation.enable = false;
}

Complete the boot and state settings before building. All hosts import the shared desktop profile automatically; you do not add another hard-coded host entry to flake.nix.

git add hosts/my-pc
nix flake check
nix build .#checks.x86_64-linux.caelestia-config .#checks.x86_64-linux.portable --no-link
sudo nixos-rebuild build --flake .#my-pc
sudo nixos-rebuild test --flake .#my-pc
sudo passwd tongy
# Validate the machine, then persist:
sudo nixos-rebuild switch --flake .#my-pc

If the account does not exist yet, set its password after activation and before logging out. Do not inherit the VM's autologin, passwordless sudo, virtualization services, SSH key or software-rendering settings on a physical computer. Hardware generation reference.

08

Fresh installation from USB

This is the advanced route. Use the NixOS installer and official installation instructions to choose, partition, format and mount the target disks. Those choices depend on your machine and desired encryption; this guide deliberately supplies no generic disk-erasing commands.

  1. Boot the installer and establish networking.
  2. Prepare and mount the target root at /mnt, including its boot partition and any other declared filesystems.
  3. Generate the target hardware configuration and place the repository on the target filesystem.
  4. Create a host using that generated configuration and the bootloader settings appropriate to this disk.
  5. Install that host, set the user password, then reboot.
# In the live installer, after the target filesystems are mounted:
sudo nixos-generate-config --root /mnt
sudo mv -T --no-clobber /mnt/etc/nixos /mnt/etc/nixos.before-flake
sudo git clone https://github.com/itstongy/nixos-config.git /mnt/etc/nixos
sudo mkdir -p /mnt/etc/nixos/hosts/my-pc
sudo cp /mnt/etc/nixos.before-flake/hardware-configuration.nix /mnt/etc/nixos/hosts/my-pc/
# Write hosts/my-pc/default.nix with target-specific boot and state settings.
sudo git -C /mnt/etc/nixos add hosts/my-pc
sudo nixos-install --flake /mnt/etc/nixos#my-pc
sudo nixos-enter --root /mnt -c 'passwd tongy'
sudo nixos-enter --root /mnt -c 'chown -R tongy:users /etc/nixos'
# Reboot only after installation succeeds.

The installer must have Git available and support flakes. Use its Nix package tools if Git is missing. After installation, the repository lives at /etc/nixos and is owned by tongy. Edit and run Git as that user; use sudo for system activation. Always pass the checkout path and host explicitly to rebuild. Official NixOS installation manual.

09

Displays, graphics and dictation

The default monitor rule chooses the preferred mode automatically. Inspect connected displays from a Hyprland session with hyprctl monitors. Set host-specific Lua declarations through tongy.monitorConfig.

tongy.monitorConfig = ''
  hl.monitor({ output = "DP-1", mode = "2560x1440@144", position = "0x0", scale = 1 })
  hl.monitor({ output = "HDMI-A-1", mode = "1920x1080@60", position = "2560x0", scale = 1 })
'';

These names and modes are examples, not facts about your displays. Use the names reported on that host. Add extra host-specific compositor settings with tongy.extraHyprland. Shared bindings and rules remain in assets/hypr/.

tongy.ghosttySoftwareRendering = true is the existing VM's workaround. It sets software rendering and disables the custom Ghostty shader for that host. Leave it at its default on physical hardware unless diagnosing a rendering problem.

# Optional host settings:
tongy.dictation.enable = true;
# Only after checking supported physical GPU behaviour:
tongy.dictation.vulkan = true;

Dictation installs the pinned model and a user daemon, plus Super + Ctrl + X. The service is intentionally skipped in VMs. A successful Nix evaluation does not validate microphone access or Vulkan on another device. Test those on the real machine.

10

What changes survive a rebuild

Kind of fileBehaviourHow to make a lasting change
Home Manager store linksRead-only generated configuration; Home Manager owns installation and removalEdit the referenced asset or Nix option and rebuild
Wrapped application configStored with its package and selected by the wrapperEdit the wrapper module or asset, then rebuild or run the new package
tongy.writableFilesWritable copies restored from the declared sources when Home Manager activatesCopy intentional GUI changes back into the relevant repository source
Unmanaged app dataApplication-managed state survives configuration rebuildsUse the app's sync/export or an independent backup

Writable copies currently cover Caelestia settings and scheme/wallpaper state, Vicinae settings, and Vesktop settings. Their GUI edits are temporary unless recorded in Git. The activation writes these before reloading Home Manager user services.

During migration from the old custom dotfile manager, known direct store links are moved to .before-home-manager backups. Repeated conflicts use numbered backups. Home Manager's normal backup command handles conflicting ordinary files. The migration skips links already owned by Home Manager.

Nix is not a personal-data backup. The repository does not contain browser sessions, cookies, Bitwarden secrets, SSH private keys, app sign-ins, Steam saves, notes, Syncthing identities or Tailscale credentials. A reproducible desktop will not recreate these.

Use distinct Syncthing device identities per machine and pair each device with the intended folders. Authenticate Tailscale separately. Review sync conflicts before connecting a fresh installation to existing data. The configuration enables these services but does not perform those account and pairing steps.

11

Recovery and troubleshooting

The pointer looks like the Hyprland logo

The shared appearance module now installs Bibata-Modern-Classic at size 24 through Home Manager. GTK and X11 use that theme, and Hyprland uses its XCursor implementation. The session receives the theme before startup. Rebuild and log in again to refresh all running applications; the compositor can also be refreshed with hyprctl setcursor Bibata-Modern-Classic 24.

A rebuild or application update fails

An evaluation or build failure normally leaves the running generation alone. Read the first substantive error. Do not delete flake.lock to make it disappear. Revert the specific source or lock change, build again, then test.

git diff
nix flake check --show-trace
sudo nixos-rebuild build --flake .#my-pc --show-trace
# To return to the previous system generation:
sudo nixos-rebuild switch --rollback

Use the bootloader's previous generation if the current one will not boot. Rollback restores configuration and packages, not arbitrary application data. An app may have migrated its database since the older generation was created.

Home Manager activation fails
systemctl status home-manager-tongy.service
journalctl -u home-manager-tongy.service -b
systemctl --user --failed
bash tests/home-manager.sh

Check for file collisions, permissions and the named failed activation step. Inspect a conflicting file before moving it. Preserve useful local edits. Do not make the whole home directory writable or run standalone Home Manager as root.

Caelestia says an option no longer exists

The installed version here is Caelestia 2.3.0. The old bar.status object was replaced by bar.statusIcons, whose entries have an id and enabled flag. bar.workspaces.displayType was removed. The repository now uses supported options and validates them through the actual pinned plugin.

nix build .#checks.x86_64-linux.caelestia-config --no-link
nix log .#checks.x86_64-linux.caelestia-config
# In the graphical desktop session:
caelestia-shell list
caelestia-shell log --help

After changing JSON, rebuild and let the shell reload it. Log out and back in if it retains stale state. Do not suppress unknown-option notifications as a substitute for fixing the config. After a nixpkgs update, rerun the config check before switching.

A keybinding cannot find an application

Check its actual executable and desktop entry. Zen's package supplies zen-beta, and the browser shortcuts now use that name. Helium supplies helium; ChatGPT supplies chatgpt.

command -v zen-beta helium chatgpt
ls /etc/profiles/per-user/tongy/share/applications
hyprctl configerrors

Changes to a running session's environment may need a fresh login. Use uwsm-app -- <command> for desktop launches, as the existing bindings do.

Storage usage is growing

Review nix.gc in modules/base.nix and the retained system generations. Garbage collection can remove old generations and unreferenced store paths. Keep a known-good generation while validating a large update; do not assume an old rollback remains available forever.

The Git commit preserves the recipe. It does not guarantee that every upstream release artifact remains downloadable indefinitely. Keep independent backups of important data and recovery media.

Machine rollout checklist

☐ Record the hardware, bootloader, disk layout and existing state version.

☐ Add a unique host with its own hardware configuration.

☐ Review the shared username, privileges, locale and installed services.

☐ Keep the VM's autologin and passwordless sudo confined to the VM.

☐ Stage new host files, run both flake checks, and build the target system.

☐ Set a login password and confirm recovery access.

☐ Test the desktop, displays, graphics, audio, networking, suspend and lock/unlock.

☐ Pair Syncthing and authenticate Tailscale; restore personal data deliberately.

☐ Test applications and optional dictation on the actual hardware.

☐ Switch permanently, reboot when appropriate, and commit the working configuration.

☐ Keep a known-good generation until the new setup is established.

Validated in the existing VM: NixOS system builds and activation, Home Manager files and services, repeated activation, portable CLI checks, Caelestia config loading, Ghostty launch, Helium browser launch and ChatGPT sign-in UI. Physical hardware installation, account login flows, authenticated ChatGPT tools, and microphone/GPU dictation remain machine-specific checks.

The new Caelestia test was also run against the previous JSON and correctly reported the two obsolete options. The corrected config passed. This tests the installed parser rather than a handwritten list of allowed keys.
